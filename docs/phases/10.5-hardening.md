# Phase 10.5 — SaaS Admin Completion & Hardening

## Summary

This phase **completes the SaaS administration layer** built in Phase 10 and addresses every follow-up item left there:

1. **Usage limits are now enforced on writes** — a transactional, isolation-safe guard re-reads the plan limit and the current count *inside the same transaction that performs the create*, so concurrent requests cannot easily bypass the cap. Wired into student creation; staff enforcement is provided as the same reusable guard (see Remaining Issues — there is no staff-creation path in the app today).
2. **Subscription renewal history** — a new immutable `SubscriptionEvent` model records `CREATED`, `STATUS_CHANGED`, `RENEWED`, `PLAN_CHANGED`, and `CANCELLED` events atomically with each subscription transition. The current subscription stays queryable in one row; historical events are never overwritten or deleted.
3. **Complete plan-management UI** — a working Edit dialog (previously a dead `/admin/plans/[id]` link / 404) covering name, slug, description, price, active toggle, student/staff limits, features (JSON), and notes. Create/Edit/Activate/Deactivate/Delete all present. All validation is server-side (zod in the action).
4. **Platform-role management** — SUPER_ADMIN can now grant/change/remove `SUPER_ADMIN` and `SUPPORT` roles on any user. Only SUPER_ADMIN can assign roles; SUPPORT cannot promote itself or anyone else; school roles remain fully separate from platform roles (Membership is untouched); removing the final Super Admin is blocked server-side to prevent lockout.
5. **Admin mobile navigation** — a Base-UI `DropdownMenu` hamburger appears below `lg` in the admin header, reusing the existing responsive approach. No new UI framework.
6. **Security review** — full re-audit of the admin surface; genuine issues found and fixed (dead plan-edit link/404, untrusted-enum ordering cleanup, UMD `React.ComponentType` reference). No architecture was redesigned unnecessarily.

All mutations remain server actions that re-verify `SUPER_ADMIN` and write audit-log entries. PostgreSQL remains unavailable (P1001) — no runtime DB verification was possible and no fake data was seeded. The full validation chain passes.

## Database Changes

### New Enum: `SubscriptionEventType`
```prisma
enum SubscriptionEventType {
  CREATED
  STATUS_CHANGED
  RENEWED
  PLAN_CHANGED
  CANCELLED
}
```

### New Model: `SubscriptionEvent`
```prisma
model SubscriptionEvent {
  id             String                @id @default(cuid())
  schoolId       String
  subscriptionId String
  planId         String
  type           SubscriptionEventType
  fromStatus     SubscriptionStatus?    // status before the transition
  toStatus       SubscriptionStatus
  startDate      DateTime?              // dates captured at event time
  endDate        DateTime?
  gracePeriodEnd DateTime?
  reason         String?
  reference      String?                // external reference (payment ref, etc.)
  actorId        String
  createdAt      DateTime               @default(now())

  school       School             @relation(fields: [schoolId], references: [id], onDelete: Cascade)
  subscription SchoolSubscription @relation(fields: [subscriptionId], references: [id], onDelete: Cascade)
  plan         SubscriptionPlan   @relation(fields: [planId], references: [id], onDelete: Restrict)
  actor        User               @relation(fields: [actorId], references: [id], onDelete: Restrict)

  @@index([schoolId, createdAt])
  @@index([subscriptionId, createdAt])
  @@index([planId, createdAt])
}
```

Relations added: `School.subscriptionEvents`, `SchoolSubscription.events`, `SubscriptionPlan.events`, `User.subscriptionEvents`.

Design notes:
- **Immutable history**: events are append-only inserts performed atomically inside the same `$transaction` as the subscription write. History can never be overwritten or deleted by business logic.
- **Current state stays simple**: `SchoolSubscription` remains one current row per school (`@@unique([schoolId])`), easy to query for gates and usage checks.
- Captured-at-transition date fields (`startDate`, `endDate`, `gracePeriodEnd`) mean historical events remain accurate snapshots even if the subscription is later edited again.

## Usage-Limit Write Enforcement

### `src/server/services/subscription-enforcement.ts`
- `UsageLimitError` — thrown when a write-side capacity check fails; carries `resource`, `current`, and `limit` for callers, and a user-safe message.
- `assertUsageCapacityTx(tx, schoolId, resource)` — runs inside the caller's **transaction**:
  - reads the school's current subscription + plan limits,
  - enforces an active subscription (ACTIVE/TRIAL, or GRACE_PERIOD while `gracePeriodEnd` is in the future; EXPIRED/SUSPENDED/CANCELLED and past-end dates are rejected),
  - re-counts the resource **inside the transaction** — `Student.count` (active, not archived) or `Membership.count` (SCHOOL_ADMIN/TEACHER),
  - throws `UsageLimitError` when the plan limit is reached; null limit = unlimited.
- The existing read-side `checkUsageLimits`/`enforceUsageLimit` remain unchanged for reporting and pre-checks.

### Wired into `src/server/actions/students.ts` — `createStudent`
The count + insert are wrapped in a single interactive transaction at `Prisma.TransactionIsolationLevel.Serializable`:

```
db.$transaction(async (tx) => {
  await assertUsageCapacityTx(tx, access.schoolId, "student");
  const created = await tx.student.create({ ... });
  return created.id;
}, { isolationLevel: Serializable })
```

Because two concurrent creates share one transaction that both re-counts and inserts, they cannot both slip past the plan limit. `UsageLimitError` is translated to a clear `fail("Student limit (N) reached.")`.

**Platform staff bypass**: when the actor is platform staff (SUPER_ADMIN triaging a tenant), the limit guard is skipped (consistent with the tenant-gate bypass and the "do not block SUPER_ADMIN/platform operations" requirement). School-scoped users are always enforced.

**Staff**: the identical helper is available with `resource: "staff"`. No staff-creation path exists anywhere in the app (`db.membership.create` is never called by any action), so staff writes cannot currently activate the guard — the helper is the enforced primitive a future staff-creation module must route through (see Remaining Issues).

## Subscription Renewal History (`src/server/services/school-subscriptions.ts`)

Lifecycle transitions now write events atomically:

| Service | Event(s) recorded |
|---------|-------------------|
| `createSubscription` | `CREATED` (with plan) |
| `setSubscriptionStatus` | `STATUS_CHANGED` (from → to) |
| `cancelSubscription` | `CANCELLED` |
| `updateSubscription` | `PLAN_CHANGED` when the plan changes; `RENEWED` when only the end date is extended forward |

`listSubscriptionEvents(schoolId)` returns newest-first history with actor name and plan name/slug for admin display.

## Platform Role Management (`/admin/users`)

- New server action `setPlatformRoleAction(userId, role)` in `src/server/actions/admin.ts`:
  - `assertSuperAdmin()` gate — only Super Admins can assign/change/remove roles.
  - Role changes are written to `AuditLog` as `USER_PLATFORM_ROLE_CHANGE` with `from → to`.
  - Removing the **last** SUPER_ADMIN is blocked (`count <= 1` → error) to prevent platform lockout.
  - Invalid roles rejected; no-op changes rejected.
- The users page now lists **all** users (not just platform-role users) so roles can be granted, ordered by role then recency, with a per-row client `PlatformUserActions` component ("Make Super Admin" / "Make Support" / "Remove role" depending on current role, "This is you" marker on self).
- Platform roles remain strictly separate: Membership rows are never touched, and school admins have no path to platform roles (no permission, no UI, and actions are SUPER_ADMIN-only).
- SUPPORT cannot promote anyone — `setPlatformRoleAction` requires SUPER_ADMIN, and SUPPORT has only read/admin `view` grants.

## Security Review

Walked every admin page/action, the permission matrix, the tenant gate, and cross-references. Findings & actions:

| Finding | Severity | Action |
|---------|----------|--------|
| Plan "Edit" navigated to a non-existent route (`/admin/plans/[id]`) | Medium (404, misleading UI) | Replaced with `EditPlanDialog`; removed all dead links to that route |
| Usage limits were read-only; concurrent creates could bypass a plan cap | High (with the requirement) | Added transactional `assertUsageCapacityTx` at Serializable isolation; wired into `createStudent` |
| Users page could not grant platform roles → no way to staff a second admin in-app | Medium | Added `setPlatformRoleAction` + UI |
| `(admin)/admin/page.tsx` referenced UMD `React.ComponentType` without an import | Low (latent) | Imported `ComponentType` explicitly |
| Users list ordering relied on `platformRole` enum sort without nuancing nulls | Low | `orderBy: platformRole asc` so platform staff sort first, null-role users last |
| SUPPORT self-promotion / school-admin role escalation | None | Already impossible: `setPlatformRoleAction` is SUPER_ADMIN-only; Membership is never written from admin actions; SUPPORT has only read "view" grants |
| Removal of the final SUPER_ADMIN | None (guard added as hardening) | Count check before any demotion/removal |

No new architecture was introduced; existing patterns (server actions + `assertSuperAdmin` + audit log, Base-UI primitives, `hidden lg:block` responsive layout) were reused.

## Remaining Issues / Follow-ups

1. **Staff usage-limit enforcement has no live call site**: No action or path in the codebase creates staff memberships (`SCHOOL_ADMIN`/`TEACHER` — `db.membership.create`/`upsert` for staff roles is never invoked; only PARENT memberships exist via `createParentUser`). The transactional `assertUsageCapacityTx(tx, schoolId, "staff")` guard is implemented and ready; the future staff-creation module must route its membership write through it at Serializable isolation, exactly as student creation does.
2. **Subscription history UI**: events are recorded and listable via `listSubscriptionEvents`, but no admin page renders the timeline yet (the school detail/subscription pages show current state only). Low-effort follow-up.
3. **Renewal detection heuristic**: in `updateSubscription`, `RENEWED` is derived from an end-date extension with an unchanged plan. An explicit "renew" action could emit a more precise `RENEWED` event (this phase favors accuracy of history over UI, so no action was added).
4. **`Throw` on missing subscription in direct service calls**: `updateSubscription`/`setSubscriptionStatus`/`cancelSubscription` throw a generic `Error("Subscription not found.")` if the row is missing inside the transaction; admin actions pre-check with `fail(...)` so end-user behavior is already friendly.
